## 哪些当前选择可以保留

| 当前选择                                 | 核对结论                       | 依据/限制                                                              |
| ---------------------------------------- | ------------------------------ | ---------------------------------------------------------------------- |
| GitHub 接入层和 Runtime 分离             | 与通用 Channel 目标一致        | 需要补适配器实际可插拔性，不能把接口存在当成已完成                     |
| 公网入口 + 内网主动连接                  | 符合已有部署条件               | 不要求 Runtime 公网可达；ECS 是实例，不是产品约束                      |
| 官方 Octokit 处理 App/签名/token         | 已复用成熟基础设施             | 不应再自研 GitHub 身份协议                                             |
| 固定服务端 task scope 与 actor 授权      | 应保留                         | 未来 GitHub 工具复用仍需包住此边界；工具参数不能扩大仓库权限           |
| 受理先落盘、结果先保存、未知副作用不重放 | 当前有测试支撑                 | 并不代表 exactly-once；未来 Runtime 的 status/cancel 能力可改善恢复    |
| 云端 Inbox 与本地 journal                | 分别覆盖网络两端故障，存在理由 | 后续复用 Runtime 持久性时要逐项比较责任，不能仅因都是 SQLite 就删一层  |
| TLS 在 edge，业务服务 HTTP               | 合理的部署分层                 | 可复用已有网关；无需为“成熟”强迫所有用户再装一个 Nginx                 |
| 当前单 worker、串行、保守 unknown        | 可作为已明示的首个里程碑边界   | 对长任务和多 Runtime 不够用，需要后续容量/生命周期设计；本轮不伪装修复 |

## 尚未定案的架构问题

1. 如何把事件、触发规则、GitHub 目标对象与 Runtime 执行请求分开，避免所有事件都被压成 comment。
2. 如何用能力声明和适配器装配接入不同 Runtime，而非让它们实现 OpenClaw Responses。
3. 哪一层负责工作区、代码编辑和项目测试；优先使用已有 Runtime/Agent SDK/Actions runner，不在核心复制编码引擎。
4. GitHub 读取、分支和 PR 发布能否复用官方 MCP/Octokit/现成 Action；现成组件的仓库/分支策略、重试和结果对账有哪些缺口。
5. 如何保存 Runtime run handle、运行状态和产物，使断连、重启、超时后可以按真实能力查询；不能把 cancel 请求发送成功当作执行已停止。
6. 如何使 Issue→代码→测试→PR 成为可验收场景，同时不把通用 Channel 限定为只做编码任务。

这些是待研究的设计问题，不是本轮已经实现的新架构。已有外部源码快照已收集，后续比较需以本次实现地图为前提，重新核对结论。
