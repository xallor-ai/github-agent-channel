# GitHub Agent Channel 产品契约

服务个人与团队：在多个 GitHub 仓库中，用户可以把工作交给自有 Agent，在原 Issue 或 PR 继续协作，并核验成果。以下是成熟版的验收目标；已交付范围与证据见[能力台账](capabilities.md)，选型依据见[调研记录](product-research-20261124.md)。

## 通道承诺

| 编号 | 能力 | 验收条件 |
| --- | --- | --- |
| C1 | 接入 | 按仓库选择 Agent、权限与事件；执行机只需出站。撤销一个仓库不影响另一个；能区分未安装、漏订阅和执行端离线。 |
| C2 | 委派 | 分析任务不改代码；只读 Agent 收到编码请求时明确拒绝，不自行换用更高权限身份。 |
| C3 | 上下文 | 从正确的仓库、线程和版本取证。PR 与默认分支不同时，读取对应 base/head 差异；材料缺失或截断须明示。 |
| C4 | 续办 | Issue、关联 PR 和后续指令可追溯。执行会话更换后仍保留任务约束；不同仓库的同号 PR 不能串线。 |
| C5 | 干预 | 用户在 GitHub 能看到接单、等待和结果，可澄清、请求停止或接管；未确认停止时显示状态未知。 |
| C6 | 成果 | 从原任务找到实际改动、验证结果和发布回执。模型陈述不算验证；仓库任务无需虚构评论目标。 |
| C7 | 授权与重投 | 区分 App 安装权限和发起人权限，外部写入前重新授权。重投不新建第二个 PR，写入结果不明时先对账。 |
| C8 | 诊断 | 管理员能从投递追到任务、运行及发布结果，无需读密钥或改库。每个声明支持的运行时组合均有独立验收证据。 |

## 工作流与通过条件

| 编号 | 交付级别 | 通过条件 |
| --- | --- | --- |
| W1 分析 | 必需 | 在 Issue 或 PR 发问、补充约束、得到有依据的关联回复；不产生代码改动。 |
| W2 编码与续改 | 必需，首要验收 | 维护者提 Issue → Agent 改代码并验证 → 创建 draft PR → 维护者在改动行提出调整 → 更新**同一 PR**并验证新 head。全程无需手贴 diff 或运维切换运行时；不覆盖人类提交，遇冲突停止说明。 |
| W3 原生评审 | 正式支持，按仓库启用 | 对实际提交发布 GitHub Review；行内意见指向正确文件和行，可在原线程复核。普通 PR 评论不计为原生评审。 |
| W4 CI 反馈 | 状态反馈必需，自动修复可选 | 展示目标 SHA 对应的检查来源、链接和状态；无权限、未运行或旧提交通过均不算本次通过。启用修复后才执行，限制轮数，并核验新提交。 |

## 职责与变更

- Channel 管 GitHub 身份、路由、任务上下文、授权、发布和回执；Runtime 管推理与编码工具，执行设施管工作区与隔离。至少一个正式支持的组合须跑通 W2，不要求所有适配器都能写代码。
- 全量事件监听、自动合并、企业多租户与计费、自建模型或沙箱均不属于基础版门槛。ECS 是可选部署。旧契约直接删除，不设兼容别名；旧库拒绝并保留。
- 功能 PR 引用对应 C/W 编号，说明复用选择、验收条件与证据。缩减承诺或扩大权限须由产品负责人确认；某个适配器的限制不能改写产品目标。
