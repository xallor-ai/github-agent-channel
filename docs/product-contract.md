# GitHub Agent Channel 产品契约

GitHub Agent Channel 是个人与团队委派、持续协作和核验自有 Agent 工作的通道。用户在多个仓库中发起任务，在原 Issue 或 PR 查看进展、提出修改并核验成果。本文规定成熟版验收目标；当前实现见[能力台账](capabilities.md)，选型依据见[调研记录](product-research-20261124.md)。

**仓库接入（C1/C2/C7/C8）：** 用户从执行端选择仓库与规则；服务端核验安装范围及配置者权限后才受理，无需逐仓修改 ECS。有效绑定决定是否入队，设备在线只影响何时执行；启用仓库不会授予写仓权限。

**持续的仓库协作：** 用户在 GitHub 发起、跟进和核验工作。绑定指定 Agent 负责哪些仓库和事件；收到活动、形成委派、获准写入是三个不同的决定。已启用的深度评审应自动取得指定版本，无需人工维护仓库副本。Runtime 可以组织子 Agent 或委派独立执行器，但委派不得扩大原任务授权；父任务应能追溯实际执行者、产物和验证。本文是目标；现有事件子集与执行组合以能力台账为准。

**默认关注的边界（[#20](https://github.com/xallor-ai/github-agent-channel/issues/20)）：** 一次配对后按仓库选择负责 Agent。默认观察支持且获准投递的活动；无法核实的订阅或权限显示未知。普通讨论进入线程上下文，不启动模型；提及、显式分诊、标签或自动评审才是行动。自己发布的回执不再唤醒自己。设备离线允许有界补领；最后一次领取时间不证明当前在线。能力声明、管理员授权及真实发布分别核验。Channel 不接管 Runtime 的子 Agent 调度。

**功能细则：** [功能地图](product-features.md)按用户旅程列出默认行为、责任人、失败边界、现状与交付顺序。普通讨论须送达但可静默；明确委派、对未决澄清的直接答复、已开启的实质性 PR 复评有反馈义务。[收件、👀 与复评](owner-feedback-spec.md)定义验收；[合并问答](pr-merge-assessment.md)规定事实、建议与写入权限的区别。

## 通道承诺

| 编号 | 能力 | 验收条件 |
| --- | --- | --- |
| C1 | 接入 | 按仓库选择 Agent、权限与事件；执行机只需出站。撤销一个仓库不影响另一个。能区分未安装、漏订阅、投递失败和执行端离线；重复投递、补投及处理结果可查，证据不足时不猜原因。 |
| C2 | 委派 | 委派前，用户可查看本仓所选 Agent 支持的任务类型。不支持的请求在执行前明确拒绝，不以部分执行代替，也不自动切换到更高权限身份。分析任务不改代码。 |
| C3 | 上下文 | 只读任务获准访问的仓库、线程和版本；PR 按实际 base/head 取差异，材料缺失或截断须明示。Issue、评论、fork、提交、文件和 CI 输出都是任务数据，其内容不能扩大权限或改变策略。 |
| C4 | 续办 | 任务身份独立于单次 GitHub 事件和 Runtime 会话。Channel 按任务保留约束，关联后续指令、运行、成果和验证；换会话仍可续办。同一 PR 可有多个任务，不能仅凭 PR 归并；不同仓库的同号 PR、无关线程不得串线。 |
| C5 | 干预 | 用户可在 GitHub 查看状态、答复澄清、请求停止或接管。接管生效后，旧运行不得再向相关工作区或 PR 发起写入；在途写入须对账。重新委派后，按最新任务状态、仓库版本及用户确认的约束重新校验写入权限。 |
| C6 | 成果 | 完成条件取自用户请求和已确认的约束；改变交付范围或通过标准须经用户确认，按原标准补做验证无需再确认。用户无需查日志，即可从原任务看清做了什么、验证结果、发布结果及是否需介入。编码成果关联提交 SHA、PR head、验证对象、对应版本的 CI / Review（如有）及发布回执。模型自述不算验证；分析无需 commit 或 PR，仓库任务无需虚构评论目标。 |
| C7 | 授权与重投 | 每次外部写入前校验 App 安装授权、发起人对目标资源的权限及任务操作范围。不满足时停止写入并说明原因；已有授权无需重复确认，新增授权由有权用户完成。重复投递不得重复写入；结果不明先对账，不盲目重发。 |
| C8 | 诊断与支持范围 | 管理员无需读密钥或改库即可从投递查到运行和发布结果。支持矩阵按「适配器、具体 Runtime/harness、影响行为的版本与执行环境」列出支持及不支持的工作流。每项支持声明须有该组合的真实场景、执行结果及可追溯记录，不得借用其他组合的证据。 |

### 任务状态的验收口径（C5、C6、C7）

| 用户看到的状态 | 判断依据 |
| --- | --- |
| 已接收 / 执行中 | 任务已持久化且可追踪才算接收；有执行端运行证据才报执行中。断连后无法确认是否仍在运行，报未知。 |
| 等待输入 | 说明等谁、需要什么，以及在哪里答复。 |
| 停止中 / 已停止 | Channel 接受停止请求即不再发起新发布，在途写入单独对账。只有执行端确认终止才报已停止，并说明已有改动是否保留、如何接管；无法确认终止则报未知。 |
| 已完成 / 失败 / 未知 | 达到该任务约定的完成条件才报完成。已知未达标报失败，证据不足报未知。PR 已创建但必需验证失败，应同时展示 PR 回执与验证失败，不报任务完成。 |

## 工作流与通过条件

**评审能看什么（C2/C3/C6/C8）：** 用户委派时能看到本仓支持的分析深度；结果说明实际检查的范围、版本与遗漏。以下是产品目标，适用所有 Runtime。分析深度与发布形式分别验收：有依据的评论可以满足 W1，只有取得原生 GitHub Review 回执才计入 W3。

| 用户要做什么 | Agent 应当能做什么 | 不足时怎样反馈 |
| --- | --- | --- |
| 线程问答 | 根据获准读取的 Issue/PR 材料解释问题、提出建议。无需准备整仓。 | 只有描述、文件名或默认分支内容时，说明依据；不能声称检查过本 PR 的代码。 |
| 评审本次改动 | 用户无需贴 diff。自动定位本 PR 的仓库、base/head 和实际差异；意见能追溯到被审版本的路径和改动。 | 二进制、不可读或被截断的部分明确列出；缺少关键材料时不下通过结论。 |
| 深度评审 | 除差异外，能在同一任务获准的源码版本中搜索未改动的调用方、实现或测试，并引用具体位置说明影响。默认提供按任务隔离的只读源码视图，用户无需手工同步仓库。 | 组合不支持时在执行前说明；运行中拿不到源码则说明缺口，不把仅看差异算作深度评审。只读分析不自动运行仓库代码或转为可写任务。 |

**版本变化：** PR 更新后，新一轮基于新版本核验。旧运行即使晚返回，也不得给新版本作通过背书；目标已关闭或合并则停止发布。两次意见都能追溯到各自的版本。产品不要求每个 Runtime 维护长驻 clone，也不要求缓存或特定沙箱实现。

| 编号 | 交付级别 | 通过条件 |
| --- | --- | --- |
| W1 分析 | 必需 | 在 Issue 或 PR 发问、补充约束、得到有依据的关联回复；不产生代码改动。 |
| W2 编码与续改 | 必需，首要验收 | Issue → 实际改动与验证 → draft PR → 维护者在改动行提出调整 → 更新**同一 PR**并验证新 head。无需手贴 diff 或运维切换运行时。 |
| W3 原生评审 | 正式支持，按仓库启用 | 对具体提交发布 GitHub Review；行内意见绑定文件、差异位置和版本。head 更新后，旧意见保留原版本归属；定位失效时标明过期，基于新差异复核，不复用旧行号。普通评论不计为原生 Review。 |
| W4 CI 反馈 | 状态反馈必需，自动修复可选 | 展示目标 head SHA、检查来源、链接及状态。新 head 不继承旧 SHA 的通过结论；无权限、未运行或仍在等待均不算通过。启用修复后限制轮数，重新核验新提交。 |

**W2 安全续改：** 写入前核对 PR 的 head、base 和期间新增的提交。head 上有人类新提交时，能安全接续就保留这些提交，仅在任务授权范围内追加修改；base 推进时重新判断集成条件。无法安全更新时停止写入，保留现有成果并说明冲突与接管方式。不得强推覆盖、丢弃或未经授权改写人类提交。

## 职责与变更

- Channel 管 GitHub 身份、路由、任务上下文、授权、发布与回执；Runtime 管推理与编码工具，执行设施管工作区与隔离。至少一个正式组合须跑通完整 W2；只声明分析的组合按 W1 验收。
- 版本上下文、只读源码与原生评审的交付顺序和真实验收场景见[实施方案](superpowers/plans/2026-11-25-pr-review-context.md)。W2 仍是首要编码闭环；深度评审不授予 W2 写权限。
- 全量事件监听、自动合并、企业多租户与计费、自建模型或沙箱不属于基础版门槛。ECS 是可选部署。
- 删除旧契约，不设兼容别名。遇旧库须报明不支持的格式及所需版本，原样保留，并指引用户备份旧库、另建新库；恢复备份不等于转换格式，不提供旧库迁移。
- 功能 PR 引用 C/W 编号，说明复用选择、验收条件与证据。缩减承诺或扩大权限须由产品负责人确认。API、存储结构和状态枚举由技术设计承接。
