# 回答“这个 PR 能合吗”

**维护者使用说明与验收规格（C3/C6/C7/C8、W3/W4）。** 对应 [#23](https://github.com/xallor-ai/github-agent-channel/issues/23)。这是针对原 PR 的只读判断，不发起合并、不绕过保护，不把普通评论升级为批准。状态查询可描述已关闭目标；不得因此在已关闭的旧 PR 上重新开工或发布。

## 如何查询

在已绑定、仍开放的同仓 PR 上评论 `@<bot> /merge-status`。OpenClaw 连接器识别该指令和部分直接提问（如“这个 PR 能合吗？”），调用无参数的 `read_merge_facts`，直接生成三项结论：PR 是否已合并、平台条件是否满足、工程上是否建议合并。该路径不调用模型，不生成批准或原生 Review。其他 PR 分析可以由模型请求同一只读工具；Issue 和仓库任务不能指定别的 PR 调用它。

云端从已授权任务读取两端仓库、PR 号和 SHA，取证前后重查当前绑定与发起人权限。检查名称和来源来自[适用于目标分支的活动 ruleset](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch)及[传统分支保护](https://docs.github.com/en/graphql/reference/branches#branchprotectionrule)，审核决定和冲突状态直接读取 [GitHub PR](https://docs.github.com/en/graphql/reference/pulls#pullrequest)。候选测试合并提交的结果与 head 分开；队列条目只能证明已入队，不能证明队列生成的新候选已通过。若要求的部署、签名或其他规则未逐项核实，报告缺项。提交者自己的合并权限和工程验收均不由此推断。

普通任务无需新增权限。查询传统保护时使用仓库限定的可选 `Administration: read`；读取检查与提交状态时使用 `Checks: read` 和 `Commit statuses: read`。某项权限不可用只影响对应证据。每个提交最多读取 100 个检查上下文，单次响应最大 512 KiB；超限按不完整处理。显式合并查询只对仍开放、快照稳定的目标请求普通回帖；是否已发布以独立的 GitHub 回执为准。

## 给维护者的答案

| 问题 | 必须核对 | 答案边界 |
| --- | --- | --- |
| 是否**已经合并**？ | GitHub 对该 PR 的开放/关闭状态及合并事实（如 mergedAt） | 分开答“已合并”“已关闭未合并”“仍开放未合并”“无法确认”。单有 CLOSED 或正文里的 Closes 不能判断已合并。 |
| **当前能合入**目标分支吗？ | 当前 base/head、draft、GitHub 冲突/计算中状态、适用的分支规则、所需检查、审核和其他门禁（例如必须经合并队列） | 单列代码是否可合并与仓库规则是否放行。无冲突但必需检查失败，答“代码无已知冲突，当前被检查阻挡”。计算中、缺权限或门禁未知就列出已知与缺项。队列可入队不等于可立即合入。不代替平台判断某位用户有合并权限。 |
| **建议现在合并**吗？ | 以上事实，加上该版本的实际评审范围、未解决的阻断、维护者约定的验收与验证 | 给出“建议”“不建议”或“证据不足”，并说明决定性依据及下一步。GitHub 允许合并与工程上建议合并可不同。无评审依据时可以报告平台状态，不能代替维护者背书。 |

**同一次判断的取证规则。** 从授权的原 PR 解析双方仓库和 SHA，读取适用规则，按目标 head 对照必需检查名称、来源、状态及链接；区分“确认没有必需项”和“看不到必需项”。审核按当前适用规则计算，不能数历史 APPROVED 数量代替有效批准。采集结束再核对 base/head；任一变化则丢弃混合结论，重新取一套事实或标记过期。检查、审核和规则在 SHA 不变时也会变化，因此答复要带查询时间。查不到一项不妨碍直接回答其他已确定问题。

**例：** “仍开放，未合并。当前版本 H2 无已知代码冲突，必需检查 `test` 仍在运行；现在不建议合入。等 H2 的检查结束后复核。”实际答复附目标 SHA、查询时间和 GitHub 检查链接。不能用 H1 的绿灯，也不能把单个 CLEAN 字段当所有门禁都通过。

## 怎么证明当时看到了什么

**门禁事实的归属。** 每项检查记录它验证的对象（PR head、GitHub 测试合并提交，或队列生成的候选提交）、发布检查的应用、对应规则和观察时间。三者的绿色结果不可互换。规则要求进队时，分别回答“可否入队”“候选组合验证到哪一步”；即使 PR head 不变，base 或前序队列成员变化也可能产生新候选。拿不到候选状态时可以说“PR 本身的必需检查已通过，队列验证未知”，不能说“可以立即合并”。

| 相同表象 | 必须区分的情况 | 给维护者的下一步 |
| --- | --- | --- |
| 页面上没有红灯 | 已证实没有必需项；有必需项但还未上报；无权读取规则 | 仅第一种可标“不要求”。第二种列出等待项；第三种指出缺哪种可见性，不要求用户绕过保护。 |
| 检查名称相同且成功 | 目标版本和必需来源一致；来自旧 SHA、其他 App 或过期队列候选 | 只采纳与适用规则匹配的结果，列出缺失的当前检查或新的队列链接。 |
| 已有批准或无未解决评论 | 满足当前规则；旧批准已被撤销或需特定审核人；普通评论或 Bot 总评没有批准效力 | 指出仍需谁或哪一类审核，不用“无人反对”代替审批。 |

**读与写分开验收。** 判断事实的只读入口必须限定原仓库和 PR。若执行中的目标已关闭，允许在授权的状态查询中显示终态；既有发布栅栏仍须阻止新的评论/Review。规划不要求为回答状态问题放开已关闭目标的写权限。无法向原线程回帖时记录结果及未发布原因，不谎报“已告知维护者”。

从触发评论能查到：任务/运行及部署版本、被查 PR、双方 SHA、采集时间、允许使用的工具、**实际调用**的工具、关键字段是否取得/缺失原因、最终三项结论及公开回执。保留必要标识和证据链接；不要求公开凭据、仓库正文、完整工具参数或模型推理链。

[#213 的提问](https://github.com/xallor-ai/xallor/pull/213#issuecomment-7185379411)与[原答复](https://github.com/xallor-ai/xallor/pull/213#issuecomment-7185406811)说明了验收差别：据 #23 的调查，当时部署为 `45b848d`，只有一次 `read_issue` 调用。任务成功且回帖已发送，仅证明交付了文本。事后查到的 OPEN、CLEAN 和 head `a9125a1` 是另一次观察，不是模型当时掌握的输入。开发分支后来能读取固定版本 diff，仍不等于已有完整的门禁查询。

## 与 GitHub 对照的验收矩阵

| 测试 PR 的事实 | 答案必须体现 |
| --- | --- |
| 开放、非 draft、无冲突、门禁均已确认满足 | 报告本版平台条件满足；单列工程建议及其证据。 |
| draft、冲突、必需检查失败 | 逐项指出真实阻挡；修复或转为 ready 后重新取证。 |
| 必需检查等待、审核不足、要求合并队列 | 分别指出等哪项检查、缺何种审核或只能入队，不把等待报为失败或通过。 |
| 已合并 / 已关闭未合并 | 给出各自终态，不再讨论“现在是否可合”，不向关闭线程发布。 |
| 权限不足、GitHub 尚未算完、规则或检查来源不明 | 明示未知字段及影响；已确定的状态照答，无依据不建议合并。 |
| 采集中 H1→H2，或 base 推进 | 旧事实留作历史，无同版新快照不能给 H2 肯定建议。 |

先用可控数据覆盖所有分支，再用真实开放 PR 对照同一次查询的 GitHub 事实、版本、工具轨迹与回执。测试全程没有合并写入。

## 实测：真实 GitHub 只读对照

**如何在原 PR 使用。** 在已绑定且接收评论的仓库，向负责的机器人单独提问“这个 PR 现在能合并吗？”或发送 `@机器人 /merge-status`。绑定 OpenClaw 时，这类问题由 Channel 直接读取 GitHub，无需模型作决定；明确的状态查询仅产生普通评论，即使绑定启用了原生评审。ACP 不承诺这条快捷路径。

**管理端核对。** 使用现有管理员身份查询 `GET /repositories/<repositoryId>/comments/<commentId>/task`，得到任务 ID、原 PR 版本、运行句柄、工具计数和回执。查看 `GET /tasks/<id>` 的历史成果，其中 `merge_assessment` 记录当时的查询时间、三项结论和缺项。运行记录的 `modelTools: []` 表示确定性路径没向模型提供工具；云端工具计数表示连接器请求，并不等于模型调用次数。若要重新查询此任务绑定的 PR，使用 `GET /tasks/<id>/merge-facts`；返回的 `current_readback` 是现在的观察，不回帖、不改写旧成果。版本变动不可用新事实替旧版本背书。

两端均从部署者提供的 `CHANNEL_BUILD_SHA` 读取完整 40 位提交号（Docker 构建参数同名）。未提供就标记未知。构建号不是运行机器上的仓库 HEAD，也不证明镜像内容经过签名验证。
