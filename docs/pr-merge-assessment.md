# 回答“这个 PR 能合吗”

**规划规格（C3/C6/C7/C8、W3/W4）。** 对应 [#23](https://github.com/xallor-ai/github-agent-channel/issues/23)。这是针对原 PR 的只读判断，不发起合并、不绕过保护，不把普通评论升级为批准。状态查询可描述已关闭目标；不得因此在已关闭的旧 PR 上重新开工或发布。

## 给维护者的答案

| 问题 | 必须核对 | 答案边界 |
| --- | --- | --- |
| 是否**已经合并**？ | GitHub 对该 PR 的开放/关闭状态及合并事实（如 mergedAt） | 分开答“已合并”“已关闭未合并”“仍开放未合并”“无法确认”。单有 CLOSED 或正文里的 Closes 不能判断已合并。 |
| **当前能合入**目标分支吗？ | 当前 base/head、draft、GitHub 冲突/计算中状态、适用的分支规则、所需检查、审核和其他门禁（例如必须经合并队列） | 单列代码是否可合并与仓库规则是否放行。无冲突但必需检查失败，答“代码无已知冲突，当前被检查阻挡”。计算中、缺权限或门禁未知就列出已知与缺项。队列可入队不等于可立即合入。不代替平台判断某位用户有合并权限。 |
| **建议现在合并**吗？ | 以上事实，加上该版本的实际评审范围、未解决的阻断、维护者约定的验收与验证 | 给出“建议”“不建议”或“证据不足”，并说明决定性依据及下一步。GitHub 允许合并与工程上建议合并可不同。无评审依据时可以报告平台状态，不能代替维护者背书。 |

**同一次判断的取证规则。** 从授权的原 PR 解析双方仓库和 SHA，读取适用规则，按目标 head 对照必需检查名称、来源、状态及链接；区分“确认没有必需项”和“看不到必需项”。审核按当前适用规则计算，不能数历史 APPROVED 数量代替有效批准。采集结束再核对 base/head；任一变化则丢弃混合结论，重新取一套事实或标记过期。检查、审核和规则在 SHA 不变时也会变化，因此答复要带查询时间。查不到一项不妨碍直接回答其他已确定问题。

**例：** “仍开放，未合并。当前版本 H2 无已知代码冲突，必需检查 `test` 仍在运行；现在不建议合入。等 H2 的检查结束后复核。”实际答复附目标 SHA、查询时间和 GitHub 检查链接。不能用 H1 的绿灯，也不能把单个 CLEAN 字段当所有门禁都通过。

## 怎么证明当时看到了什么

从触发评论能查到：任务/运行及部署版本、被查 PR、双方 SHA、采集时间、允许使用的工具、**实际调用**的工具、关键字段是否取得/缺失原因、最终三项结论及公开回执。保留必要标识和证据链接；不要求公开凭据、仓库正文、完整工具参数或模型推理链。

[#213 的提问](https://github.com/xallor-ai/xallor/pull/213#issuecomment-7185379411)与[原答复](https://github.com/xallor-ai/xallor/pull/213#issuecomment-7185406811)说明了验收差别：据 #23 的调查，当时部署为 `45b848d`，只有一次 `read_issue` 调用。任务成功且回帖已发送，仅证明交付了文本。事后查到的 OPEN、CLEAN 和 head `a9125a1` 是另一次观察，不是模型当时掌握的输入。开发分支后来能读取固定版本 diff，仍不等于已有完整的门禁查询。

## 与 GitHub 对照的验收矩阵

| 测试 PR 的事实 | 答案必须体现 |
| --- | --- |
| 开放、非 draft、无冲突、门禁均已确认满足 | 报告本版平台条件满足；单列工程建议及其证据。 |
| draft、冲突、必需检查失败 | 逐项指出真实阻挡；修复或转为 ready 后重新取证。 |
| 必需检查等待、审核不足、要求合并队列 | 分别指出等哪项检查、缺何种审核或只能入队，不把等待报为失败或通过。 |
| 已合并 / 已关闭未合并 | 给出各自终态，不再讨论“现在是否可合”，不向关闭线程发布。 |
| 权限不足、GitHub 尚未算完、规则或检查来源不明 | 明示未知字段及影响；已确定的状态照答，无依据不建议合并。 |
| 采集中 H1→H2，或 base 推进 | 旧事实留作历史，无同版新快照不能给 H2 肯定建议。 |

先用可控数据覆盖所有分支，再用真实开放 PR 对照同一次查询的 GitHub 事实、版本、工具轨迹与回执。测试全程没有合并写入。
