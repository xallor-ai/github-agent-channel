# 仓库负责人：产品边界与验收

对照 [#20](https://github.com/xallor-ai/github-agent-channel/issues/20)。GitHub 是维护者的工作台。Channel 把已授权的仓库活动交给配对设备上的指定 Agent，保留原线程、任务与发布回执。下表区分本分支行为和未交付能力。

| 问题 | 此前的偏差 | 现在如何判断 | 尚不能承诺 |
| --- | --- | --- | --- |
| 谁负责 | 绑定指向设备，运行时另配；同一设备改了 agentId 仍可能领取原任务 | 仓库绑定保存设备、管理员和负责 Agent 的类型及 ID；领取与活动查询匹配当前负责人。设备内换负责人须重新 apply，规则更新使旧修订失效。 | 不会转移另一设备的绑定，也没有多个 Agent 竞争接单或自动改派。 |
| 能看到什么 | 事件过滤也是执行过滤，非提及讨论消失 | 默认观察支持且获准投递的事件；普通讨论保留为不可信背景。授权的设备按仓库分页读取。bridge 在后台有界补领，持久化进度和截断状态；不把普通讨论作为新的模型指令。 | 不主动向 OpenClaw 会话推送每条消息；适配器支持的运行能力不代表 GitHub 已投递，未知也不是零事件。 |
| 何时执行 | 监听 PR/push 等同于要求模型开工 | 普通讨论、非删除分支 push、关闭活动不唤醒；明确提及或仓库显式配置的行动才建任务。相同 PR 版本的重复自动评审复用决定；机器人回帖不唤醒自己。 | 未实现所有 GitHub 事件；不凭模型推断取消、批准或扩大权限。 |
| 能做什么 | 深评和原生 Review 两头重复配置，授权容易被理解为已执行 | 仓库授权一次，与负责人支持能力取交集；普通回复、固定提交的 COMMENT Review 和受写入策略约束的 draft PR 是不同结果。 | 配置不能证明真实发布；不能将 Review 当作批准合并。 |
| 状态能证明什么 | 用户手抄修订，难区分没有安装、没有投递和没有执行 | CLI 提交前读取修订，并发冲突显示差异；可查看订阅/权限覆盖、活动原因和关联任务。最近一次有效领取证明曾经联系，不能证明此刻空闲。 | 用户看不见的订阅、权限或连接状态不能用猜测补齐。 |
| 谁委派子任务 | 容易把安装了多个 Runtime 理解为会自动协作 | Channel 负责 GitHub 身份、范围、持久记录和发布；Runtime 负责选择和调度子 Agent。 | OpenClaw → Codex → 原 PR 续改/复审、父子任务关联与证据回传尚未端到端验收。 |

**验收方式。** 从空的当前版本状态库，用[管理员最小声明](agent-self-service.md)绑定真实测试仓库。记录普通评论、提及、PR 更新、同版本重复投递、push 和关闭的 delivery ID、活动原因、模型调用数与实际发布回执。先验证普通评论是“一条活动、零任务、零模型调用、零发布”，再验证一次明确委派只产生一次有效执行。离线后补读、换负责人拒绝旧任务及撤权后禁止写入须独立核验。SQLite/HTTP 测试是回归证据，不替代这项线上验收。
