**第一项开发任务：** 在现有只读 PR 任务上构造一次按 base/head 固定的上下文读取；暂不增加写权限。先在 [GitHub 客户端测试](../tests/github.test.ts) 和 [pull 协议测试](../tests/pull.test.ts) 写出“默认分支与 PR 内容不同”“未授权不读取”“两次读取间 head 变化不混用版本”三个用例，再补实现、真实验证和 Channel 评审。

## W2 验收记录模板

第 3 项接管与隔离门槛通过后，才进行真实续写验收。H1 指第二轮取证时已包含维护者修改的 PR head SHA，H2 指 Channel 本轮更新后确认的 head SHA。

| 步骤 | 真实操作 | 必留证据 |
| --- | --- | --- |
| 首次委派 | 在受控仓库 Issue 明确范围与必需验证，创建 draft PR | 原 Issue、稳定工作标识、首轮 run、PR 编号和初始 head |
| 人类参与 | 维护者向该 PR 提交一处可区分的修改，并在改动行提出续改 | 人类提交 SHA、取证时的 H1、评论与线程链接、目标行、第二次投递 |
| 第二轮交付 | Agent 从 H1 续办；不手贴 diff、不手切 runtime，更新同一 PR | 第二轮 run、新 head H2、H1 仍在 H2 历史中、人类改动仍保留、无第二个 PR |
| 用户核验 | 在原 Issue 查看 H2 的验证、发布回执及是否需要介入 | 对应 H2 的报告/CI、任务最终状态、用户可见链接 |
| 独立异常用例 | 另起一次运行，在发布前推进 head、撤权、接管或重投；注入响应丢失 | 各场景分别记录预期/实际、副作用次数、在途写入对账；注明真实试验还是自动化替身 |

每个切片结束：核对目标编号 → 运行行为测试 → 通过 Channel 评审指定 base/head 和实际 diff → 核验评审意见 → 更新台账。CI 通过或模型回帖都不代替真实 W2；证据不齐保留“待验收”。
