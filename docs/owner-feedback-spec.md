# 仓库负责人如何收件、答复和复评

**目标与验收规格。** 当前已实现逐事件收件确认及明确提及后的独立 👀；OpenClaw 的结构化澄清支持在原线程无 @ 续办。自动评审会记录可查的取代依据，真实多版本验收尚未完成。操作见[自助接入](agent-self-service.md)。 对应 [#20 绑定](https://github.com/xallor-ai/github-agent-channel/issues/20)、[#21 负责人反馈](https://github.com/xallor-ai/github-agent-channel/issues/21)、[#22 收件回执](https://github.com/xallor-ai/github-agent-channel/issues/22)；承接 C1/C2/C4/C5/C6/C7/C8、W1/W3。用户应能在原线程得到答复，或查清为什么这件事没有公开回复。

## 一条消息的四份证据

| 用户看到什么 | 谁确认，依据是什么 | 不能据此声称什么 |
| --- | --- | --- |
| Channel 已接收 | 服务端验签、核验绑定，持久保存原投递、来源评论/线程、处理原因及可选任务关联。重复投递指向原决定。 | GitHub 发出请求或返回 HTTP 200，不足以证明负责人已收到。 |
| 已送达负责人 | 当前绑定修订的指定 Agent **接收端**确认已接收具体事件；确认必须可在重启后核验。可以由代表该 Agent 的持久收件箱代收，前提是事件对其可消费且确认可关联到原评论。 | 云端入队、领取租约、设备心跳、桥接器累计计数或仅保存游标都不是逐条确认；不代表模型已读懂。 |
| 已处理 | 负责 Agent 或其明确配置的策略留下对应事件的处理决定：静默、待澄清、已形成结果、失败，或被哪个更新取代。允许不调用模型的静默决定。 | “一直没回帖”不是静默决定；失败和失联不能标记已处理成功。 |
| 已公开反馈 | Channel 在原目标核验本次评论或原生 Review 的 GitHub 身份、链接、关联任务及适用版本。 | 👀 不是答复；有回帖也不证明答对、测试通过或可以合并。 |

这不是每条事件都必须走到第四步的流水线。普通讨论可以停在“已处理：静默”；必须反馈的任务不能这样结案。执行状态、收件回执和公开反馈分别查询。离线显示待送达；超出保留窗口显示缺口及补充材料入口，不能事后补记已送达。

## 哪些情况必须答

| 触发与范围 | 负责人的动作 | 原线程交付 |
| --- | --- | --- |
| 开放 Issue/PR 中两位维护者普通讨论，没有提及 | 送达同一负责 Agent，保留两条来源。可合并临近消息处理，不按每条评论启动推理。 | 可静默；若主动澄清或回复，仍需仓库策略允许且通过发布授权。默认不加 👀。 |
| 有权用户明确提及并委派工作或提问 | 绑定原评论与任务，说明结果、必要的澄清或可确定的失败。 | 必须反馈。遇到写入被禁止或结果不明，向状态查询者说明，不冒充已回帖。 |
| 用户不再提及，直接回答负责人上一次澄清 | 提问时记录原任务、问题标识、期望答复者和线程。优先按明确引用或问题标识关联；同一线程仅有一个匹配的未决问题且答复者匹配时可续接。 | 原任务继续，说明新证据使原判断维持、修正或仍缺什么。多个未决问题或答复对象不明时请求指定问题，不凭相邻时间猜关联、不开第二个编码任务。 |
| 已启用自动评审，开放 PR 的新提交改变被审内容 | 固定新的仓库、base/head，读取真实差异，复核旧意见是否仍适用。 | 必须给出发现、无新增发现或未能完成及原因。原生模式成功以新 commit 的正文型 COMMENT Review 为准；不再重复发一条“评完了”。 |
| 未启用自动评审的 PR 更新、普通 push、关闭或机器人自身评论 | 依策略记录活动或历史回执。其他 Bot/不支持的资源按观察范围说明。 | 不因观察获得写权限。关闭、合并或撤权截断待发布写入；已经发出的操作另行对账。 |

**版本竞争。** 同一轮 PR 评审以仓库、PR、生命周期和 base/head 确定归属。push 和 synchronize 指同一提交时不能重复开评。H2 等待期间 H3 到达，可只评 H3，但必须能从 H2 查到“被 H3 取代”；运行中的 H2 未确认停止时不能写“已停止”，也不能发布为 H3。空提交只有在比较基线与实际被审内容均核验未变时才可跳过，并说明依据；新 SHA 的 CI、审批和 Review 回执仍独立。普通讨论合并处理也保留每一个事件的收件归属。

## 👀 是独立的收件回执

- **只放在哪里：** 明确提及或明确回答未决澄清的有权人类用户，且来源是可核验的 Issue/PR 会话区评论。由 Channel 在该条原始 comment ID 上以 App 身份加一个 eyes。Issue 正文、push、普通讨论、其他 Bot、自身回声及行内 Review 评论不使用这个入口。
- **何时添加：** 先持久化逐事件接收确认，再异步发布 reaction；写前复查绑定、来源、权限与线程。离线时不加，领取但未确认时不加。确认后的 👀 保留为历史事实，不因最终成功或失败而删除；无需等待表情写入才开始处理。
- **怎样对账：** 用仓库 ID、原评论 ID、App 身份及 eyes 匹配，只认可该身份的 reaction ID。成功新建与同身份已存在均可确认；别人的 👀 不算。响应丢失先读取现有 reaction；403、限流、评论删除、无法确认分别记录，不盲目重发、重启模型或改发顶层评论。参考 [GitHub issue-comment reactions](https://docs.github.com/en/rest/reactions/reactions#create-reaction-for-an-issue-comment)。

## 交互与恢复规则（规划）

| 现场情况 | 决定与用户可见结果 | 验收时刻意制造的反例 |
| --- | --- | --- |
| 领取之后接收端崩溃，或批量补领三条消息 | 接收端应能按绑定修订、接收者、原始事件逐条查询确认；批次也要能展开到单条。只有已确认的明确委派可发 👀。 | 第三条尚未确认时重启：前两条可对账，第三条仍待送达，不能按批次末尾游标替三条盖章。 |
| 收件与换负责人交错 | 已发生的收件保留原接收者；未确认的旧绑定消息不能记到新负责人名下。原任务需交接时，明确展示交给谁及从哪个未决问题继续。 | A 已接收但尚未发表情时改绑 B：停止旧绑定的新写入，不能让 B 自动补 A 的 👀 或重复开工。 |
| 一条答复可能同时匹配两个未决问题，或作者修改已处理过的评论 | 保存问题与原任务的关系；冲突时给出可选的问题引用，让用户明确。编辑不是一条新委派；尚无编辑事件支持时，不声称已纳入修改。 | 原问题已被回答，随后又收到同一答复的重投：回查已有处理和公开结果，不第二次运行。 |
| 一次处理横跨多个阶段 | 原线程保留一份有用的最终交付；进度优先在同一任务记录更新，不按每次工具调用另发评论。必须反馈但无法写回时，状态列出受阻原因、最后可证实的阶段与可执行的下一步。 | reaction 写入失败而正式 Review 成功：展示两个独立结果，不将整个任务标成发送失败，也不再补一条总结。 |

**复评基线如何选择。** 增量只允许从同一仓库、同一 PR、同一生命周期且已核验覆盖范围的上次评审出发。记录上次评审的 base/head、当前 base/head、这次看过的范围和仍未检查的部分。force-push 后旧 head 不在当前历史、基线推进导致比较语义变化、上次材料截断或无法证明提交完整时，重新审当前 PR 相对新基线的完整差异。仍取不到完整材料就说明缺失；不得宣布“全量通过”。区别于执行状态未知后的重跑：新版本复评是新的授权决定，不补发旧任务的不明写入。

验收另加两例：H2 只改一处但 H1 上次仅做了局部评审，不得对全 PR 作无阻断结论；H2 经 rebase 且 base 前进，必须能指出重评范围与原结论失效的原因。

## 上线门槛

| 场景 | 必须同时看见的证据 |
| --- | --- |
| 在线与离线各一条明确提问；对同一条重投 | 在线确认后才有本 Bot 的一个 👀；离线仅有接收记录，恢复确认后才有 👀。查询能从原评论分别找到接收确认、reaction ID 和最终答复。 |
| 两条普通评论，随后负责人提问、作者无 @ 补证据 | 普通消息都有送达证据，可静默且无自动表情；补证据续回原任务，必须反馈。加入第二个未决问题时不会串线。 |
| H1/H2 实质差异、快速 H2/H3、空提交、同 SHA 重投 | 各版本均有决定及理由；新版本有自己的事实和唯一已核验的反馈；被取代的版本不冒领新结果。 |
| 授权撤销、关闭竞态、reaction 写失败及回帖响应丢失 | 未发送的写入被拦截；在途结果按原资源对账。表情失败不阻塞正常答复，公开反馈失败不抹去真实收件记录。 |

真实验收保留仓库、线程、源评论/投递、负责 Agent/绑定修订、任务/运行、各阶段时间、模型调用次数、版本及 GitHub 回执。普通讨论尤其要核对“已送达”和“零次不必要公开写入”同时成立；样例截图、Webhook 日志或本地测试不能替代。
