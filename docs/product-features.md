# 产品功能地图与交付顺序

[产品契约](product-contract.md)定义成熟版承诺；本页按维护者的使用顺序解释每项承诺的入口、责任边界和通过条件。**目标、分支已实现、生产已验收是三个不同判断。** 下表的现状对照开发分支 `5ea5cce`；具体实现和证据以[能力台账](capabilities.md)为准。

| 功能（承诺） | 谁在什么情况下使用 | 正常交付；失败或越界怎么办 | 现状与验收重点 |
| --- | --- | --- | --- |
| 连接设备、绑定仓库（C1/C2/C7） | 运营者部署服务一次；设备所有者连接 Agent；仓库管理员选择仓库及负责人。 | 确认安装范围、管理员身份、负责人及有效策略；冲突展示差异，不覆盖。不为新仓库重复配置 ECS 或授予个人 token。 | 分支已实现最小绑定；验证错设备、错负责人、停用和并发改配。[角色与操作](agent-self-service.md) |
| 观察协作变化（C1/C4） | 已绑定、受支持且获授权的活动，无需每条 @。 | 记录源事件与线程；负责人离线可有界补领。范围外、受限、被截断和未知要可区分。 | 已有活动账本及桥接器游标；**逐条送达/处理确认仍待补**。[证据定义](owner-feedback-spec.md) |
| 委派、分诊与反馈（C2/C5/W1） | 用户明确提问，或管理员开启适用的标签、分诊、自动评审。 | 明确委派必答；普通讨论可静默。不能让只支持编码的组合因自动分析规则而动手改代码。 | 已有行动策略；待补必答义务跟踪、静默决定及失败可见性。[场景表](owner-feedback-spec.md) |
| 收件提示（C5/C6） | 人类在原评论明确提及，或直接答复待澄清问题。 | 逐事件确认后才允许由 Bot 加一个 👀；收件、执行、最终回答各自取证。 | 规划，未验收。先做确认再做 reaction；验收离线、重投、评论删除及响应丢失。[规则](owner-feedback-spec.md) |
| 续办、澄清、停止与接管（C4/C5/C7） | 用户补充证据、要求停止或接管未完成任务。 | 以原任务及未决问题标识续办；归属不明先澄清。接管后禁止新增写入，在途写入单独对账；恢复前刷新约束与版本。 | 线程背景及关闭栅栏不等于完整任务控制。待验原问题无 @ 续办、两任务不串线、未确认停止不报已停。 |
| 版本取证与深评（C3/W1/W3） | 用户评审同仓 PR；需查跨文件影响时显式启用深评。 | 固定 base/head，执行机按需获取只读源码；引用实际位置，说明遗漏。拿不到源码不能伪称完成深评。 | 已有固定差异、缓存与搜索；真实探针和完整生产验收分开。[评审指南](pr-review.md) |
| 持续复评与原生 Review（C4/C6/W3） | 开放 PR 有实质改动且已授权自动评审。 | 新版获得发现、无新增发现或失败原因。原生模式发布固定 commit 的 COMMENT 总评；不重复发总结评论，不批准或合并。 | 已有同版本去重和发布前复查；被取代版本、空提交及各版必答待验。行内发布不在当前支持范围。[版本规则](owner-feedback-spec.md) |
| 编码、验证与同一 PR 续改（C3/C6/C7/W2） | 获准编码的用户在 Issue 委派，维护者在原 PR 提出修订。 | 独立可写环境修改约定范围，保存实际产物和验证 SHA，按策略建 draft PR；续改同一 PR 且保留人类提交。冲突时停止写入并说明接管方法。 | 有 ACP 编码和 draft PR 的单段证据；不能代验完整两轮续改。[编码验收记录](acp-live-validation-20261124.md) |
| CI、门禁与合并问答（C3/C6/W4） | 维护者问“合了吗、现在能合吗、建议合吗”。 | 对本版规则、检查和审核逐项取证；回答三件事，未知列缺项。问答不触发合并或自动修复。 | 完整事实读取、工具审计及真实对照待实现。[判定表](pr-merge-assessment.md) |
| 授权、发布与故障恢复（C6/C7/C8） | 任一外部写入、断连、重投或人工核验。 | 每次写入复查身份、绑定、目标与权限；执行、reaction、评论、Review、draft PR 各有回执。未知先对账，不能靠再次调用模型恢复。 | 已有任务/发布记录和部分对账；待补逐事件收件证据与逐工具可见性。[运维](operations.md) |
| 子 Agent 委派（C2/C4/C6/C8） | 负责 Agent 把编码或复核交给独立执行者。 | Runtime 决定派给谁；Channel 追踪父任务、子运行、权限范围、版本和产物；只有获准发布方写回原线程。 | 规划。单独配置 OpenClaw 和 ACP 不算已实现 OpenClaw→Codex 编排；验收一条真实父子链，含子运行失联。 |

**实施依赖：** 先补每条消息的负责人接收确认和待澄清任务关联（#21）；👀（#22）依赖前者，不能拿表情代替确认。版本复评与取代记录依赖已有的 PR 版本和任务标识。合并事实读取与工具审计（#23）可以并行，不依赖表情功能。最后用同一开放 PR 串验：普通讨论送达 → 委派确认 → 澄清续办 → 新 head 复评 → 用户询问合并，逐项核对**应该发生以及不应该发生的模型调用、写入和回执**。W2 编码闭环保留独立验收，不因这条只读旅程通过而标为完成。

**W2 与子任务怎样一起验收（规划）。** 同一 Issue 委派修复，负责 Agent 把编码交给已授权的执行器。原任务记录子运行、允许变更的范围与工作起点；子运行交回实际改动和验证对象，不能仅回一句“已修好”。创建 draft PR 后，维护者提交自己的修改，再在该 PR 要求续改：执行器必须以含人类提交的新 head 为起点，保留其历史，在同一 PR 提交结果并重新验证。若接管时子运行失联，分别显示“停止已请求／终止未知”和“外部写入待对账”；在结果明确前不得启动另一个写者。通过条件是维护者能从原 Issue 核对父子任务、两轮 head、保留的人类提交、验证及发布回执。此项仍未端到端验收。

[社区依据与取舍](community-workflow-decisions.md)解释为何采用任务关联、保守选择增量基线和区分队列检查，同时不把新调度器或自动合并纳入 Channel。
